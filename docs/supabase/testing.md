# Authentication test plan

## Automated checks

- TypeScript compilation: `npx tsc --noEmit`
- Lint: `npm run lint`
- Production build: `npm run build`

## Supabase checks

Before testing OAuth, verify the provider is enabled in the same Supabase
project referenced by `NEXT_PUBLIC_SUPABASE_URL`. The public Auth settings
endpoint can confirm provider state without exposing credentials, but provider
secrets must still be checked in the Supabase Dashboard.

For the current local configuration, the project URL resolves to
`https://vjifcnvrmnyqyvuirdns.supabase.co`. Google must be enabled under
Authentication → Providers and configured with a Google Web Client ID and
Client Secret before the Google button can work.

Run these checks in a non-production Supabase project:

1. Create a user through the app and confirm the `handle_new_user` trigger
   creates a profile with the default `customer` role, but do not treat the
   unverified account as active.
2. Before verification, open `/tenant-dashboard` directly and confirm the
   request returns to login with an email-verification message.
3. Resend the verification email and confirm the cooldown prevents repeated
   requests.
4. Click a valid verification link and confirm the callback returns to login
   with a success message.
5. Sign in, refresh, and call a protected server route; the session cookie
   should still identify the same verified user.
6. Change the profile display name as the signed-in user; read another user’s
   profile and confirm RLS denies it.
7. Sign out and confirm protected route access redirects to `/login`.
8. Repeat the sign-in and callback flow for Google.
9. Use expired or malformed verification callback codes and confirm the app returns to the
   login page without creating a session.

## Provider/admin RBAC checks

Run these checks after applying `0017_tenancy.sql`, `0018_media_assets.sql`,
`0019_rbac_hardening.sql`, and `0020_provider_onboarding_guards.sql`:

1. Submit a provider application as a verified customer and confirm the
   applicant remains `customer`, the application is `pending`, and the user
   cannot open `/tenant-dashboard`.
2. Sign in as a provider and confirm `/tenant-dashboard` works only for the
   provider's own business. Attempting to submit an application decision or
   change `profiles.role` must fail.
3. Sign in as an admin and confirm `/admin/provider-applications` loads, while
   `/tenant-dashboard` does not. The admin review page should show only active
   private-document links generated by short-lived R2 URLs.
4. Reject a pending application with a reason and confirm its status becomes
   `rejected` without creating a business or changing the applicant role.
5. Approve a pending application and confirm the status becomes `approved`, the
   applicant role becomes `provider`, and exactly one pending business is
   created for that provider.

## Guest-to-provider onboarding checks

1. Open **Get Listed** while signed out and confirm Business and Services can
   be completed without an authentication prompt.
2. Continue to Identity and confirm the existing login/signup dialog opens.
3. Confirm the draft business and service fields survive login or OAuth
   redirect, while identity files are not stored in session storage.
4. Confirm an unverified account cannot submit an application.
5. Confirm the final application row uses the authenticated user's ID and
   cannot be submitted with a client-supplied applicant ID.
6. Refresh the List Your Business page after submitting and confirm the latest
   application status and rejection reason are displayed.
